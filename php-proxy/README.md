# php-proxy

Файлы для `jobtoo.ru/api/`. Заливаются по FTP, как и раньше.

| Файл | Зачем |
|---|---|
| `db.php` | Всё общение приложения с базой |
| `tg.php` | Вебхук телеграм-бота |
| `admin.php` | Дашборд: вход и доступ к таблицам `jm_*` |
| `expo-updates-proxy.php` | Обновления приложения |

## Два файла, которых нет в репозитории

Оба лежат только на хостинге и в git не попадают — иначе ключи оказались бы
в открытом доступе. Расширение `.php` тут не для красоты: если кто-то
запросит такой файл по прямой ссылке, сервер выполнит его и отдаст пустоту,
а не содержимое.

### `sb_service_key.php`

Сервисный ключ из Supabase → Settings → API → `service_role`.
Образец: `sb_service_key.example.php`.

Пока файла нет, прокси работает на старом публичном ключе — то есть ничего
не ломается, но и защиты нет. Появился файл — можно применять миграцию
`supabase/migrations/013_lock_down_rls.sql` и закрывать базу от анонимного
доступа.

### `admin_credentials.php`

Логин и пароль для входа в дашборд. Образец: `admin_credentials.example.php`.

Это единственная преграда между интернетом и всей базой, поэтому пароль
нужен длинный и нигде больше не используемый. Перебор ограничен: десять
неудачных попыток с одного адреса — и вход закрыт на 15 минут.

Смена пароля мгновенно обесценивает все выданные токены: они подписаны
ключом, который выводится из пароля.

## Как это устроено

Раньше и приложение, и дашборд ходили в Supabase с публичным ключом. Ключ
этот по своей природе виден всем — он лежит в бандле сайта. Пока RLS
выключены, с ним читались телефоны, хеши паролей и вся переписка.

Теперь наружу не уходит ни один ключ. Приложение зовёт `db.php` по имени
операции — их 94, всё остальное отклоняется. Дашборд ходит через `admin.php`,
и тот пропускает запрос только с действующим токеном и только к таблицам
`jm_*`. Сервисный ключ подставляется уже на сервере.
